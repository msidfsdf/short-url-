# 阶段2 版本说明书 —— RabbitMQ 异步点击统计

> 阶段定位：在阶段1 单体架构基础上，引入 RabbitMQ，把「跳转点击统计」从请求关键路径中异步化解耦，解决高并发下每次点击都同步打一次 DB 写的瓶颈，并实现削峰 + 失败兜底。

---

## 一、本阶段用到的技术（每个技术解决什么问题）

| 技术 | 解决了什么问题 |
|---|---|
| **RabbitMQ（消息队列）** | 把"点击 +1"这个写库副作用从跳转请求路径中剥离，请求线程不再阻塞等写库；突发流量下消息在 MQ 堆积、消费者按节奏消费，天然削峰。 |
| **spring-boot-starter-amqp** | Spring 对 RabbitMQ 的官方封装，自动装配 `RabbitTemplate`、监听容器工厂、消息转换器，零样板代码接入。 |
| **DirectExchange + 队列 + RoutingKey** | 点到点精确路由：跳转发到指定交换机+路由键，唯一消费者队列接收，语义清晰、无多余广播开销。 |
| **Jackson2JsonMessageConverter** | 消息体以 JSON 序列化，可读、可跨语言、便于排查；Spring Boot 自动装配到生产者与消费者。 |
| **手动 ACK（MANUAL）+ basicNack(requeue=false)** | 入库成功才确认；失败拒绝且不重入队 → 进死信队列，避免失败消息无限重投导致队列阻塞、影响正常消息。 |
| **死信队列（DLX）** | 承接消费失败的消息，等待人工排查或重放，保证核心队列不被"毒消息"拖垮。 |

---

## 二、现阶段解决的问题（瓶颈来源）

阶段1 的跳转接口 `getOriginalUrl()` 中，每次点击都会同步执行一次 `click_count = click_count + 1` 的 `UPDATE`。这意味着：

- 每次点击都打一次 DB **写**（读路径才需要同步，写是副作用）。
- 点击频率 ≈ 写库频率，高并发下 DB 写入成为最大瓶颈，且请求线程被写库阻塞。

> 注：跳转"查原 URL"是硬依赖（必须当场拿到返回值才能发 302），**无法**用 MQ 优化；能优化的只有"点击 +1"这个与响应无关的副作用。这是引入 MQ 的精确理由。

## 三、工作流程（简化版）

```
用户点击短链
   │
   ▼
[跳转接口] 查 Redis → 未命中查 DB → 回写缓存 → 拿到原 URL
   │
   ├─ 同步：返回 HTTP 302 重定向（立即响应用户，不等待统计）
   │
   └─ 异步：发送 ClickMessage{shortCode, timestamp} 到 RabbitMQ
                                              │
                                              ▼
                                  [消费者] 手动 ACK
                                              │
                              ┌───────────────┴───────────────┐
                         成功 basicAck                  失败 basicNack(requeue=false)
                              │                              │
                              ▼                              ▼
                     click_count = click_count+1    进入死信队列(DLX)，待排查/重放
```

**核心收益**：写库与请求路径解耦 → 请求线程不再被写库阻塞；流量高峰时消息在 MQ 排队、消费者匀速消费，实现削峰。

## 六、关键设计点（面试可讲）

1. **为什么引入 MQ 而不是微服务**：本系统规模小，无需微服务；真正瓶颈是"写副作用"，MQ 恰好解决这个问题，二者职责不同。
2. **读无法 MQ、写可以**：查原 URL 必须同步返回，点击 +1 与响应无关 → "读留在线，写丢给 MQ"。
3. **跳转不能被 MQ 阻塞**：生产者 `try/catch` 包裹，MQ 宕机只记日志，302 照常返回（统计可丢失，不可挡）。
4. **可靠性兜底**：手动 ACK + 死信队列，失败消息不重投、不丢、可排查。
5. **演进方向**：消费者可由"每条一次 UPDATE"升级为"批量聚合 +1"进一步削峰；`timestamp` 字段预留给阶段3 点击趋势分析。

## 七、本地启动验证

1. 启动 RabbitMQ（本机需先安装 Erlang + RabbitMQ，或 `docker run -d -p 5672:5672 rabbitmq:management`）。
2. 启动后端 `short-url-server`（端口 8081），观察到消费者容器 `acknowledgeMode=MANUAL` 即表示监听就绪。
3. 创建短链 → 访问短链（302 跳转）→ 查看 DB `click_count` 是否异步 +1，或 RabbitMQ 控制台 `short-url.click.queue` 是否有消息被消费。

> 编译验证：`mvn compile` BUILD SUCCESS；`spring-boot:run` 在 broker 未启动时报 `Connection refused` 但应用照常启动，证明跳转不被 MQ 可用性影响。

## 八、Bug 修复记录

阶段2 开发过程中发现并修复了两个真实 bug，均源于阶段1 MVP 的假设在阶段2 场景下不再成立。

### Bug 1：过期短链在缓存存活期内仍能跳转

**现象**：创建了 `expireSeconds=60` 的短链，60 秒后 DB 层已判定过期，但 Redis 缓存仍存活 7 天 → 接下来 7 天内命中缓存的请求照样 302，过期机制形同虚设。

**根因**：缓存写入时 TTL 固定用配置的 7 天（`cacheTtlDays`），与短链自身的 `expireTime` 无关；而缓存命中路径不做过期检查（只查 Redis 就返回），只有缓存未命中走 DB 路径才检查 `expireTime`。三个"各自都对"的功能组合出了洞。

**修复**：缓存 TTL 取 `min(cacheTtlDays, 到 expireTime 的剩余时长)`，缓存随短链同步死亡。在 `ShortUrlServiceImpl` 新增 `calcCacheTtlSeconds()` 辅助方法，`createShortUrl()` 写缓存和 `getOriginalUrl()` 回写缓存两条路径统一调用，消除不一致。

**教育点**：功能增量开发时容易出现"各自独立正确、组合产生漏洞"——缓存 + 过期是典型的两个功能交界处，必须放在一起想。review 代码时专盯这种跨功能边界。

### Bug 2：并发创建同一长链可能产生多个短码

**现象**：`createShortUrl()` 用"先 SELECT 查重 → 没有则 INSERT"防重复。两个并发请求同时到达时，都 SELECT 不到、都 INSERT → 同一长链生成两个短码（ID 不同、短码不同）。

**根因**：阶段1 建表时 `idx_original_url` 是普通索引而非唯一索引，DB 层不拦截重复；且当时隐含假设"单人使用不会有并发创建"，在压测场景下被打破。

**修复**：两层防线——
1. DB 层：`original_url(191)` 前辍唯一索引（MySQL 5.5 utf8mb4 单索引限 767 字节，191×4=764 刚好不超限；绝大多数 URL 在前 191 字符就不同）
2. 代码层：`createShortUrl()` 捕获 `DuplicateKeyException`，并发竞争时回查已有记录返回，不会产生重复短码

**为什么不直接用全列唯一索引**：本机 MySQL 5.5.40 + utf8mb4，`500×4=2000` 字节超出 InnoDB 767 限制。MySQL 8+ 建议升级后改用全列唯一索引。当前前缀索引实际可接受（99.99% 场景下够用），生产环境升级 MySQL 后改。

**教育点**："先查后插"永远有竞态窗口——并发请求在 SELECT 和 INSERT 之间穿透。数据库唯一约束才是最终防线，SELECT 查重只是快速路径优化，不能替代 DB 约束。
