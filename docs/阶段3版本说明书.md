# 阶段3 版本说明书 —— MQ 消费端批量聚合

> 阶段定位：在阶段2「RabbitMQ 异步点击统计」基础上，解决消费端遗留的**数据库写放大**问题。把「每条点击消息 1 次 UPDATE」改为「批内按短码合并后 1 次 UPDATE +N」，在慢下游约束下把系统的可持续消费速率提升约 100 倍。
>
> 基线：`2037ac0`（阶段2 定稿）。本阶段所有代码改动均在该提交之上。

---

## 一、本阶段用到的技术（每个技术解决什么问题）

| 技术 | 解决了什么问题 |
|---|---|
| **Spring AMQP 批量消费**（`consumerBatchEnabled` / `batchSize` / `receiveTimeout`） | 让监听容器不再逐条交付，而是攒够 N 条或等满超时后整批交付，为"批量合并写库"提供前提。 |
| **`List<Message>` 监听器签名 + 手动取 deliveryTag** | 绕开 Spring AMQP 3.1.7 批量模式下 `@Header(AmqpHeaders.DELIVERY_TAG)` 注入失效的问题（详见第七节踩坑 1）。 |
| **HashMap merge 聚合** | 批内按 `shortCode` 合并出现次数：`[a,a,b,a]` → `{a:3, b:1}`，纯内存操作、零 I/O。 |
| **`UPDATE click_count = click_count + N`** | 把 N 条消息的 N 次写压成 M 次写（M = 批内唯一短码数）。加法可合并且顺序无关，终值完全等价。 |
| **批量 ACK（`basicAck(lastTag, multiple=true)`）** | 一次 RPC 签收整批，把 N 次 ACK 网络往返降为 1 次。 |
| **失败逐条 NACK（`requeue=false`）→ 死信队列** | 整批失败时保证每条消息都触发 DLX，保持 at-least-once，可人工排查/重放。 |
| **MySQL `Com_update` 全局计数器** | 压测期精确统计真实 UPDATE 次数（替代"数日志行"，避免日志 I/O 成为干扰项）。 |

## 二、现阶段解决的问题（瓶颈来源）

阶段2 把「点击 +1」异步化后，请求路径是干净了，但**消费端留下了写放大**：

```
每条 ClickMessage → 1 次 UPDATE
1 万次点击        → 1 万次 DB 写
```

真正的风险在**持续流量**下暴露。设单次 DB 写耗时 `L`（慢下游场景 `L=30ms`），单消费者串行：

| 模式 | 消费速率 | 1 万次点击落库耗时 |
|---|---|---|
| 阶段2 逐条 | `1 / L` = 约 **33 条/秒** | 约 **300 秒** |
| 阶段3 批量（batch-size=100） | `100 / L` = 约 **3300 条/秒** | 约 **3 秒** |

若线上点击流持续高于 33 条/秒，逐条模式下队列会**每秒净增、永不排空**，最终撑爆 broker 内存触发流控，进而反噬接口 QPS。批量聚合把消费能力上限抬到 3300 条/秒，消除这个风险。

**关键认知：优化的不是"跑得更快"，而是"每趟搬得更多"。** 慢下游让每趟至少 30ms，这个绕不过去；批量聚合让每趟从搬 1 块变成搬 100 块——**往返次数（DB 写次数）不变，总搬运量提升 100 倍**。

## 三、工作流程（简化版）

```
① 用户请求 GET /{shortCode}
      ↓
② Redis 命中 → 立刻 302（用户感知 ~100ms，与写库无关）
      ↓
③ convertAndSend → click.exchange → click.queue（发布侧，fire-and-forget）
      ↓
④ 监听容器攒批：满 100 条 或 等满 200ms（receiveTimeout=250ms）
      ↓
⑤ 整批交付为 List<Message> 给消费者
      ↓
⑥ HashMap 按 shortCode 合并：N 条 → M 个唯一短码
      ↓
⑦ recordClickBatch：M 次 UPDATE click_count = click_count + N_i
      ↓
⑧ 成功 → basicAck(lastTag, multiple=true) 一次签收整批
   失败 → 逐条 basicNack(requeue=false) → 全部进死信队列
```

## 五、关键设计点（面试可讲）

### 5.1 为什么"合并"不会让统计失真

点击计数是**加法且顺序无关**：30 个 `+1` 与 1 个 `+30` 数学上完全等价。所以攒批不存在"少统计"或"统计错误"的风险。

实测四组压测的 `DeltaRatio`（click_count 增量 ÷ 成功请求数）**全部为 1.0000**，即 0 丢失、0 重复增益。

### 5.2 批量 ACK 与失败语义

- 成功：`channel.basicAck(lastTag, true)` —— `multiple=true` 签收所有 `deliveryTag ≤ lastTag` 的消息，一次 RPC 搞定整批。
- 失败：**逐条** `basicNack(tag, false, false)` 而非 `basicNack(lastTag, multiple=true)`。逐条写法保证每条都触发 DLX，便于死信对账；代价是整批失败时网络往返为 N 次，但这是异常路径，可接受。
- 语义：手动 ACK + 死信兜底 = **at-least-once**。整批重投会放大重复消费面，但对点击统计业务而言误差仅是少量重复 +1，可接受。

### 5.3 为什么删掉了 `batch-enabled` 开关

初版保留了 `batch-enabled=false` 退化成逐条消费的分支，**它是死代码**：容器在 `consumerBatchEnabled=false` 时走单条适配器，会把单个 JSON Object 直接喂给 `List<ClickMessage>` 参数而反序列化失败——方法体内的 `if (!batchEnabled)` 永远执行不到。

**根本原因**：单条与批量的监听器方法签名不兼容，无法用一份代码兼得。需要"逐条"基线做 A/B 时，直接用阶段2 原始代码打包即可，不靠开关切。

### 5.4 反序列化失败的批如何处理

批内若存在反序列化失败的消息，`payloads.size() != deliveryTags.size()`，此时**无法安全签收子集**（`basicAck(multiple=true)` 会签掉不该签的），实现上选择整批 NACK 进死信，交由人工排查。

## 七、踩坑记录（重要！）

### 坑 1：Spring AMQP 批量模式取不到 deliveryTag

监听器写成 `List<ClickMessage> + @Header(AmqpHeaders.DELIVERY_TAG) List<Long>`，运行时每批抛：

```
Missing header 'amqp_deliveryTag' for method parameter type [interface java.util.List]
```

**后果**：整批拒收，**四组压测 SQL 执行次数均为 0**，而当时无人发现。

**排查**：试图用 `factory.setBatchAckMode(AcknowledgeMode.MANUAL)` 开启注入，但该版本（spring-amqp 3.1.7）**根本没有这个方法**，编译报"找不到符号"。

**解决**：改用 `List<Message>` 原始消息参数 + `message.getMessageProperties().getDeliveryTag()` 手动取，并用 `ObjectMapper` 反序列化消息体，彻底绕开 header 解析。

### 坑 2：`batch-enabled=false` 是死代码

见 5.3。实测对照组 **56374 次反序列化失败、0 次落库**——那个"逐条分支"从未被执行过。

### 坑 3：压测脚本把"读取失败(-1)"当成"队列已空(0)"

`queue_depth()` 在读不到时返回 `-1`，而排空判断写的是 `if d <= 0`，于是 `-1` 被当成排空成功。四组压测全部显示 `QueueDrained=True` 的假象。

**解决**：改用 MySQL `click_count` 稳态判定（连续 N 次轮询不变即认为消费结束）。

### 坑 4：竞争消费者

压测期间 IntelliJ 中运行着另一个 short-url 实例，与压测后端抢同一个队列（约占 19% 消息），导致批量组的 UPDATE 计数从理论值 995 虚高到 19559。

**解决**：压测前必须确认 8082 无监听、且无其他 short-url 的 java 进程。

### 坑 5：MyBatis SQL 日志造成不公平干扰

MyBatis 开了 `StdOutImpl` 逐条打印 SQL，对照组（10 万次 UPDATE）日志量远大于实验组（约 1000 次），825MB vs 17KB——同步 stdout I/O 不公平地拖慢对照组。

**解决**：压测时通过 `-Dmybatis-plus.configuration.log-impl=org.apache.ibatis.logging.nologging.NoLoggingImpl` 关闭，UPDATE 次数改用 MySQL `Com_update` 计数器统计。

### 坑 6：`git stash push -- <pathspec>` 毁掉本地对象库

为切换代码版本执行 `git stash push -- <5个文件>`，报 `fatal: ... is not a valid object`，随后 `.git/refs` 目录消失、**`.git/objects` 被清空**（仅剩 6 个对象，无 pack）。

**解决**：从远端重新 fetch 恢复（远端完好）。**此后一律用 `git diff HEAD -- <files> > xxx.patch` 导出补丁 + `patch -p1 -R` 反向应用来切换版本，不再用 stash。**

## 八、压测结论

完整数据见 `docs/QPS压测报告.md` 第六章。核心结果（同一场、四组均 `VERDICT: PASS`、落库率 100.00%）：

### 8.1 稳定收益

| 指标 | 阶段2 逐条 | 阶段3 批量 | 变化 |
|---|---|---|---|
| DB UPDATE 次数（10 万次点击） | 99,500 | **995** | **-99%** |
| DB UPDATE 次数（1 万次点击 / 30ms） | 10,000 | **100** | **-99%** |
| 全量落库耗时（0ms，10 万次） | 52.2s | **7.7s** | -85% |
| 全量落库耗时（30ms，1 万次） | 376.8s | **8.9s** | **约 -97.6%** |

> 注：落库耗时含约 5 秒的稳态确认开销（连续 5 次轮询不变才判定收敛）。扣除后 30ms 场景约为 371s → 3.9s，**约 95 倍**，与 100:1 的压缩比一致。

### 8.2 未兑现的预期（已证伪并写入报告）

原预期「批量聚合后吞吐反超同步」，**实测被证伪**：

| 模式（0ms，10万/500并发） | QPS | p50 | p99 |
|---|---|---|---|
| **同步写库（阶段1 路径）** | **9227.9** | **45.64** | **104.15** |
| MQ 逐条（阶段2） | 4672.8 | 100.51 | 252.38 |
| MQ 批量（阶段3） | 4224.6 | 119.34 | 249.93 |

批量聚合的 QPS 仅为同步模式的 **45.8%**，比 MQ 逐条还低 9.6%。

**根因**：单条消息约 60 字节，10 万条合计约 6MB，远未触及 RabbitMQ 默认内存高水位 → **broker 流控从未触发**，队列堆积也就从未拖累 QPS。真正的 QPS 天花板在**发布侧**（JSON 序列化 + 发往 broker 的一跳往返 + publisher-confirm 回执），批量聚合不解决它。

**修正后的定位**：批量聚合解决的是**数据库写压力**与**最终一致性收敛速度**，不是接口吞吐。

## 九、简历口径

### 可写

> - 针对 MQ 消费端"每条消息一次 UPDATE"造成的数据库写放大，设计批量聚合消费：容器侧攒批 → 消费端 HashMap 按短码合并 → 单次 `UPDATE click_count = click_count + N`，将 DB 写次数从 O(N) 降为 O(N/100)
> - 压测验证：10 万次点击的 DB 写次数由 99,500 降至 995（**-99%**）；模拟下游 30ms 延迟时全量落库耗时由 376.8s 降至 8.9s，系统可持续消费速率由约 33 条/秒提升至约 3300 条/秒
> - 可靠性：手动 ACK + 死信队列，整批成功才 `basicAck(multiple=true)`，失败逐条 NACK 进死信，保持 at-least-once；终值一致性误差为 0
> - 排查并修复 Spring AMQP 批量模式下 deliveryTag 注入失效导致整批拒收、零落库的问题

### 不可写

- ❌ 「QPS 提升 X%」—— 实测批量版 QPS 略低于逐条版
- ❌ 「接口响应时间 / p99 优化」—— 两组场景方向不一致，属噪声
- ❌ 「吞吐反超同步」—— 已证伪

### 面试加分讲法

> 「我预判批量聚合能提升最大 QPS，因为消费端是瓶颈。实现后压测发现 DB 写次数降了 99%、收敛快了约 100 倍，但 QPS 完全没动。回头排查发现瓶颈假设错了——消息太小，队列根本没长到触发 broker 流控，QPS 天花板其实在发布侧。于是我把优化目标重新定义为降低数据库写压力与收敛时间，而不是接口吞吐。」

## 十、下一步方向

1. **真正提升 QPS**：方向在发布侧——关闭 `publisher-confirm-type` / `publisher-returns`（权衡可靠性），或批量发布。
2. **消费者并发**：`@RabbitListener(concurrency="N")`，但受 Hikari 连接池（默认 10）约束，需同步调大池或配合批量。
3. **压测方法改进**：稳态确认开销（约 5 秒）应从落库耗时中扣除，或改用更灵敏的收敛判定。
