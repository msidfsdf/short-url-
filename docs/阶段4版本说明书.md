# 阶段4 版本说明书 —— 缓存穿透 / 击穿治理

> 阶段定位：在阶段3「MQ 消费端批量聚合」基础上，解决跳转链路最容易被攻击的两个缺陷——**缓存穿透**（攻击者拿不存在的短码打 DB）和**缓存击穿**（热 key 失效瞬间几千请求同时回源）。用**四层防护链路 + 三种可切换模式**治理，同一份 jar 跑 A/B 对照压测。
>
> 基线：`73b8eb9`（阶段3 文档）。本阶段所有代码改动均在该提交之上，**未提交、未推送**，全部在工作区。

## 一、本阶段用到的技术（每个技术解决什么问题）

| 技术 | 解决了什么问题 |
|---|---|
| **Redisson `RBloomFilter`** | 挡穿透：判"一定不存在"直接 404，连 Redis 都不碰。墙画在 Redis（多实例共享 + 重启不失忆），用 SETBIT/GETBIT 基础命令拼成，Redisson 内部用 Lua 把 k 次 GETBIT 压成 1 次往返 |
| **`CacheValue` 逻辑过期包装**（JSON：`u`/`e`/`n`） | 挡击穿：把"判断过期的权力"从 Redis 物理 TTL 拿回应用层，value 里存时间戳 `e`，应用自己 `System.currentTimeMillis() > e` 判断，Redis 只给 2 倍物理 TTL 兜底防内存泄漏 |
| **`RedisLock` SETNX + Lua 释放** | 挡击穿：抢到锁的线程回源，防误删别人的锁（value=UUID + Lua 比对）。逻辑过期模式也用锁，但锁的是"异步重建触发权"不是"DB 访问权" |
| **空值缓存**（`CacheValue{n:true}`） | 兜布隆误判的漏网之鱼：布隆说"可能存在"但 DB 没有，查完写空值标记 TTL 120s，1% 误判只查 1 次 DB |
| **`CacheGuardMetrics` 11 个 AtomicLong 计数器** | 可观测性：压测期与 MySQL `Com_select` 交叉验证数据真实性；曾靠它反推出 logical-expiry 冷启动 bug（见第七节踩坑 1） |
| **`short-url.cache-guard.mode` 三态开关** | A/B 基线对照：`none`（阶段1~3 原逻辑）/ `mutex` / `logical-expiry` 三种模式同一份 jar 切换，代码路径完全独立，对照有效 |
| **MySQL `Com_select` 全局计数器** | 压测期精确统计真实 SELECT 次数（替代日志行数，避免 I/O 干扰） |

## 二、现阶段解决的问题（瓶颈来源）

阶段3 把点击统计异步化后，跳转链路 `getOriginalUrl` 还是阶段1 的裸逻辑：

```
GET /{shortCode} → Redis 没命中 → SELECT → 返回
```

两个攻击面：

### 2.1 缓存穿透

攻击者拿 5000 个随机瞎编的短码（如 `zzzz99`、`abcd12`，**格式合法但 DB 没有**）打过来。每个都未命中 Redis → 每个都打 DB → DB 每秒被白嫖 5000 次查询。

格式校验救不了这批请求——它们长得就是正经短码的样子。

### 2.2 缓存击穿

某个热 key（比如 `4c9g`）的 Redis TTL 到期瞬间，几千个并发请求同时未命中 → 同时回源 DB → DB 瞬时被几千次相同查询打。

阶段1 的裸逻辑没做任何防护，500 并发实测 DB 被打 14 次（部分靠 MySQL 查询缓存兜住），p99 高达 202ms。

### 2.3 两个缺陷的区分（面试易混点）

| | 穿透 | 击穿 |
|---|---|---|
| 数据状态 | **根本不存在** | 真存在，但缓存没了 |
| 触发方式 | 持续攻击 | TTL 到期瞬间 |
| 治理层 | ①格式校验 + ②布隆 + ④空值缓存 | ③缓存策略（mutex/logical-expiry） |

## 三、工作流程（四层防护链路）

```
GET /{shortCode}
      ↓
   [mode 切换] mode=none → 阶段1~3 原逻辑（A/B 基线）
                 mode=mutex / logical-expiry → 走下面四层
      ↓
① 短码格式校验    长度 1~10 且只含 62 进制字符集
                 非法输入连布隆都不用问, 直接 404 (O(1) 内存)
      ↓
② 布隆过滤器      判"一定不存在"直接 404, 零 DB 查询 (挡穿透)
                 预热期没就绪时 mightContain 返回 true, 宁可漏防不可误杀
      ↓
③ 缓存策略        mutex: 抢锁 + 双重检查 + 没抢到的等待重试 (挡击穿)
                 logical-expiry: 旧值先返回 + 抢锁提交异步重建 (挡击穿)
      ↓
④ 空值缓存        布隆误判漏过来的非法短码, 查完 DB 后写空值标记
                 TTL 120s, 1% 误判只查 1 次 DB (挡穿透兜底)
      ↓
                  DB
```

**四层谁也替不了谁**：① 挡"输入根本不像短码"（`x<script>` 等），② 挡"格式合法但没登记过"（`zzzz99` 等），③ 挡"真存在但缓存没了"，④ 兜"布隆说可能存在但 DB 真没有"。

## 五、关键设计点（面试可讲）

### 5.1 mutex vs logical-expiry 的本质区别（最高频考点）

| 维度 | mutex 互斥锁 | logical-expiry 逻辑过期 |
|---|---|---|
| 用锁吗 | ✅ 用 | ✅ **也用**（很多人误以为不用） |
| 锁的作用对象 | 锁"**线程进 DB**"的入口 | 锁"**异步重建任务的触发权**" |
| 抢到锁的人干啥 | 同步回源 DB，**自己阻塞**等查完 | 提交异步任务回源，**自己立即返回旧值** |
| 没抢到锁的人干啥 | **等**（sleep+重试+双重检查） | **不等**（直接拿旧值返回） |
| 失效瞬间 DB 被打几次 | 1 次 | 1 次 |
| 失效瞬间是否有旧值 | 没有（Redis key 真没了） | **有**（key 还在，只是 value 时间戳过了） |
| 失效瞬间 p99（实测） | 144ms | 36ms |
| 一致性 | 强一致 | 可能短暂返回旧值 |
| 适用场景 | 库存/余额（强一致） | 短链/文章（能容忍旧值） |

**一句话定论**：两者都用锁、都把 DB 查询从几千次降到 1 次，**区别只是"其他线程要不要等"**。选择标准是**业务能否容忍短暂旧值**。本项目 `original_url` 创建后不变，所以选 logical-expiry。

### 5.2 logical-expiry 的三个关键细节

**细节 1：失效 ≠ Redis key 没了。**
- mutex：靠 Redis **物理 TTL** 过期 → TTL 到点 key 真消失 → 没旧值
- logical-expiry：过期时间存 value 字段 `e` 里、应用自己判断；Redis 物理 TTL **故意设成逻辑过期的 2 倍** → 逻辑过期那段时间里 key 还在 → 有旧值可用

**细节 2：锁的作用变了。**
- mutex 锁：独占"DB 访问权"——没抢到的人**必须等**（没旧值）
- logical-expiry 锁：独占"异步重建触发权"——没抢到的人**不等**（有旧值先用着）。锁只是防多个线程重复触发重建

**细节 3：有 mutex 做冷启动兜底。**
`getWithLogicalExpiry` 开头 `if (cv == null)` 分支会**降级调用 `getWithMutex`**：处理"从未缓存过"、"Redis 重启后旧值被删"、"阶段1~3 遗留的裸 URL"。冷启动完成后写回 `CacheValue` JSON，逻辑过期机制重新激活。降级场景罕见：只有"逻辑过期之后 5 分钟内零访问"的极冷 key 才触发，而极冷 key 本身不存在击穿风险。

### 5.3 Redis 过期策略 vs 本项目 logical-expiry（最容易混的概念）

| 层面 | 谁负责 | 关心什么 |
|---|---|---|
| A. Redis 怎么删过期 key | Redis 服务端 | 惰性删除 + 定期删除（八股必背） |
| B. 应用怎么应对击穿 | 你的 Java 代码 | mutex vs logical-expiry |

**两者名字里都有"过期"纯属巧合，是两个独立层面，不存在对应关系。** `application.yml` 配置的是 B，不是 A；Redis 的过期方式改不了、配置文件也碰不到。

logical-expiry 故意绕开 Redis 这套机制——把"判断过期的权力"从 Redis 拿回应用层，value 里存时间戳 `e`，应用自己判断，毫秒级精确。

### 5.4 布隆过滤器的本质

**一句话本质**：用空间效率换准确率的存在性预筛器。不存数据，只回答"肯定不存在"或"可能存在"，**单边准确**——说没就一定没、说有九成九。

**四参数合同**：n（预期插入量）+ p（误判上限）是配的，m（位数组大小）+ k（hash 次数）是按公式 `m=-n·ln(p)/(ln2)²`、`k=m/n·ln2` 算出来的。本项目 n=100万 / p=1% → m≈9.6M bit (1.2MB) / k=7。

**误判来源**：hash 碰撞——多个元素的 k 个位置共用灯泡，没登记的元素碰巧算到别人全点亮的位置 → "全亮" → 误判。

**三个坑**：
1. 不能删元素 → 短链不做物理删除，业务设计消化缺陷
2. 误判率随填充率上升 → n 按 1~2 年未来规模配，不按当前数据量
3. 预热期没防护 → `isReady()` 返回 false 时放行到后面链路（宁可漏防不可误杀）

### 5.5 布隆过滤器的选型淘汰赛

| 候选 | 墙画在哪 | 致命伤 |
|---|---|---|
| Guava `BloomFilter` | JVM 堆（私有） | 单机不共享、重启随 JVM 失忆 |
| RedisBloom 模块（`BF.ADD`） | Redis 服务端 | 要 Redis 4.0+ + 装模块，咱们是 3.2.100 装不上 |
| 自研（曾试过 240 行） | Redis 进程 | 能跑通但相比 Redisson 无性能优势、维护成本高、面试讲不动 |
| **Redisson `RBloomFilter`** ✅ | Redis 进程 | 无硬伤，代价只有预热逐条 add |

**当选理由**：墙在 Redis（共享持久），手册 Redisson 写好（成熟免背），业务代码通过薄包装层隔离（将来换实现零改动）。

## 七、踩坑记录（重要！）

### 坑 1：逻辑过期模式冷启动必须写 `CacheValue` JSON，不能写裸 URL

第一版冷启动路径 `getWithMutex` 写的是裸 URL，导致后续 `CacheValue.parse` 恒为 null → 永远走冷启动分支 → `logicalExpired` 恒为 0，逻辑过期机制形同虚设。

**是靠计数器发现的**：4 次请求却 `cacheMiss=5`、`cacheHit=3`，反推出每次都走冷启动（第 1 次被计了两次 miss）。这印证了"取数双保险"的必要性——如果没有计数器，只会看到功能正常、延迟正常，根本发现不了机制没生效。

**修法**：抽出 `writeCacheValue()`，按当前 mode 选择存储格式。

**加分讲法**：面试讲"逻辑过期一度完全失效，是计数器把它揪出来的"——体现**可观测性本身就是工程能力**，比堆砌方案更能说明问题。

### 坑 2：MySQL 查询缓存会让 A/B 对照失真

本机 MySQL 5.5 默认 `query_cache_type=ON`（15MB）。击穿组是"同一个短码被反复查"，相同 SQL 会命中查询缓存，`Com_select` 不计数。开着它等于给基线组开外挂：DB 明明被打了 14 次，`Com_select` 只涨 5 次，**严重低估治理前的真实压力**。

**修法**：压测脚本已内置开始时 `SET GLOBAL query_cache_type=OFF`，结束时自动恢复 `ON`。

### 坑 3：Windows 上 JVM 日志默认 GBK 编码

`grep` 搜中文全部失败（还会把文件判为 binary），Python 按 utf-8 读也是乱码。

**修法**：启动时加 `-Dfile.encoding=UTF-8` 根治；读历史日志要按 gbk 解码。

### 坑 4：RedissonClient Bean 放进 CacheGuardConfig 触发循环依赖

本次会话改造 Redisson 时初版把 `RedissonClient` Bean 放在 `CacheGuardConfig` 里，而 `CacheGuardConfig` 构造器注入 `RedisBloomFilter`，后者又依赖 `RedissonClient` → 循环依赖 → Spring 容器启动失败，11 个测试全挂。

**修法**：拆出独立的 `RedissonConfig.java`，与 `CacheGuardConfig` 解耦。这坑是面试可讲的素材：**Spring 循环依赖为什么构造器注入救不了**（只有 setter 注入或 `@Lazy` 才能解，但拆类更干净）。

### 坑 5：压测 QPS/延迟数字只能当相对参考

客户端是 Python urllib + 线程池，并发能力上限决定了 QPS 天花板（约 2000~2500），远低于服务端真实能力；延迟里也混入了客户端侧排队时间。因此结论只用 DB 查询次数和计数器做定性判断。

## 八、压测结论

完整数据见 `docs/QPS压测报告.md` 第八章。核心结果（穿透组 5000 随机不存在的短码 / 并发 300；击穿组 清缓存后 500 并发打同一热 key）：

### 8.1 治理效果

| 场景 | 指标 | none（基线） | mutex | logical-expiry |
|------|------|-----:|------:|---------------:|
| 穿透组 | 打到 DB 次数 | **5000** | **0** | **0** |
| 穿透组 | MySQL `Com_select` 增量 | 5001 | 1 | 1 |
| 击穿组 | 打到 DB 次数 | **14** | **1** | **1** |
| 击穿组 | QPS | 1504.6 | 1920.9 | **1924.6** |
| 各自失效瞬间 | p99 (ms) | 202.56 | 144.09 | **36.26** |

### 8.2 三大结论

1. **穿透归零**：5000 假短码 DB 查询 5000→0，应用计数器与 MySQL `Com_select` 增量完全吻合（5000↔5001、0↔1），互相印证数据可信。
2. **击穿近零**：DB 查询 14→1（−92.9%），QPS +27.7%（来自消除回源等待而非 DB 变快）。
3. **logical-expiry 失效瞬间零等待**：500 个请求中仅 11 个感知到过期——异步重建在毫秒级完成，p99 36ms。

### 8.3 两种击穿方案怎么选（易错，勿混淆）

不能拿"击穿组的 mutex"与"逻辑过期组的 logical-expiry"直接横向比，**起始状态不同**：
- 前者是 Redis TTL 到期、缓存彻底消失（冷启动尖峰）
- 后者是缓存仍在、只是内容变陈

各自的"失效瞬间"对比才有意义：mutex 144ms p99 且有线程等待，logical-expiry 36ms p99 且零等待。

**真正的价值主张**：logical-expiry 让"缓存彻底消失"这件事在生产中几乎不再发生。mutex 模式下每 7 天 TTL 到期必然来一次冷启动尖峰；logical-expiry 下缓存永远是热的，只会变陈，而变陈的代价是 1 次异步重建 + 零请求等待。代价是可能短暂返回旧值——本项目 `original_url` 创建后不变，可以接受；库存、余额这类强一致场景不适用。

### 8.4 单元测试

```

  实测误判率 = 0.005% (1/20000)，配置上限 1%
  位数组 = 9585059 bit (1170 KB)，hash 函数 = 7 个       [n=100万, p=1%]
  穿透测试: 请求 300, 打到DB 0, 布隆拦截 300
  击穿测试: 50 并发, 打到DB 1, 抢锁成功 1
  空值缓存: 首次 DB 查询 0, 后续 20 次 DB 查询 0
```

参数推导与理论公式完全吻合（`m = -n·ln(p)/(ln2)²`，`k = m/n·ln2`）。**误判率 0.005% 远低于配置的 1%，原因是只填了 20%（插入 2000 / 预期 10000）——误判率随填充率上升。**

## 九、简历口径

### 可写

> - 定位跳转链路的缓存穿透与击穿两个缺陷，用四层防护链路治理：格式校验 + 布隆过滤器 + 互斥锁/逻辑过期缓存策略 + 空值缓存
> - 随机非法短码打到 DB 次数从 5000 降为 0（MySQL `Com_select` 交叉验证）；热点 key 失效瞬间 DB 查询从 14 次降为 1 次，QPS 提升 27.7%
> - 实现互斥锁与逻辑过期两套可切换方案并做对照压测，逻辑过期方案下缓存失效瞬间 p99 36ms、请求零等待
> - 布隆过滤器用 Redisson RBloomFilter（Redis Bitmap 共享持久，n=100万 / p=1%，墙约 1.2MB）；分布式锁自研（Redis SETNX + Lua 原子释放防误删）
> - 11 个单元测试覆盖误判率、不漏判、穿透/击穿行为；压测数据用 MySQL `Com_select` 与应用计数器双路交叉验证

### 不可写

- ❌ 绝对 QPS 数字（受 Python 客户端限制，见第七节踩坑 5）
- ❌ "误判率 0.005%"（那是低填充率下的结果，面试官追问填充率会露馅）
- ❌ "布隆过滤器自研"（已改用 Redisson，不再自研）

### 面试加分讲法

> 「我预判批量聚合能提升最大 QPS，因为消费端是瓶颈。实现后压测发现 DB 写次数降了 99%、收敛快了约 100 倍，但 QPS 完全没动。回头排查发现瓶颈假设错了——消息太小，队列根本没长到触发 broker 流控，QPS 天花板其实在发布侧。于是我把优化目标重新定义为降低数据库写压力与收敛时间，而不是接口吞吐。」（阶段3 的加分讲法）

> 「阶段4 的逻辑过期一度完全失效，是计数器把它揪出来的。第一版冷启动写的是裸 URL，导致 CacheValue.parse 恒为 null，逻辑过期机制形同虚设。但功能正常、延迟正常，没计数器根本发现不了。这让我意识到可观测性本身就是工程能力——不是堆砌方案，而是验证方案是否真的在生效。」
