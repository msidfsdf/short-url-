> 阶段定位：在阶段4「缓存穿透/击穿治理」基础上，堵上**短码连号可枚举**这个数据泄露漏洞——攻击者写个 for 循环扫 `4c92/4c93/4c94...` 就能把全部短链（含用户隐私、内部跳转）扒光。用 **Feistel 网络双射置换**治理，顺带修正生产配置 `log-impl` 的 IO 事故隐患。

## 一、本阶段用到的技术（每个技术解决什么问题）

| 技术 | 解决了什么问题 |
|---|---|
| **Feistel 网络**（32 位块 / 10 轮 / 10 个固定子密钥） | 防枚举核心：把自增 id 做**双射置换**（bijection）后再 Base62 编码。连号 id → 完全无规律的混淆值，攻击者无法从短码推算下一个短码。双射保证**零碰撞**（数学性质，不靠运气）+ **可逆**（decrypt 反推 id） |
| **Base62Utils（复用，零改动）** | 混淆后的数值 → 62 进制短码。它是「翻译官」，只干进制转换，不掺混淆逻辑 |
| **黄金值回归测试**（golden values） | 保护 KEYS 子密钥：把 `encrypt(1_000_000)=4195963162`、短码 `4zXPHc` 硬编码进测试断言。任何人改了 KEYS/轮数/轮函数，单测立刻红，防止「老短码全部对不上 id」的生产事故 |
| **`NoLoggingImpl`**（MyBatis-Plus） | 修生产配置隐患：`StdOutImpl` 会把每条 SQL 打到 stdout（同步阻塞 IO），高并发下 IO 吃满拖垮 JVM。压测 3 闸里「stdout<20MB」防的就是它 |

## 二、现阶段解决的问题（漏洞来源）

### 2.1 主问题：短码连号可枚举（数据泄露）

阶段1~4 的短码 = `Base62.encode(id)`，id 是数据库自增主键：

```
id=1000000 → 4c9g
id=1000001 → 4c9h    ← 除了最后 1 位，整串短码完全可预测
id=1000002 → 4c9i
```

攻击面：**for 循环遍历 62 进制字符串空间，从小到大扫**，命中 302 就拿到一条真实短链。DB 里有多少条、id 集中在哪一段，几乎能全量扒光。短链背后可能是用户隐私链接、内部系统跳转——这是教科书级的信息泄露漏洞（OWAPT 里叫 "Insecure Direct Object Reference"，IDOR 的变体）。

### 2.2 次问题：`log-impl: StdOutImpl` 生产 IO 隐患

`StdOutImpl` 是 MyBatis-Plus 给开发者调试用的：每执行 1 条 SQL 打印 1 份完整 SQL+参数+结果集到控制台。功能完全正确，但高并发下控制台输出是同步阻塞 IO，线程卡在写日志上；日志滚文件撑爆磁盘、IO wait 飙升。**性质是「开发残留配置」不是功能 Bug**——类似把 debug 开关带上了生产。

## 三、工作流程（生成链路怎么变，跳转链路为什么不用变）

### 3.1 生成短链（唯一改动的链路）

```
长链入库拿自增 id (BIGINT, AUTO_INCREMENT 从 1000000 起)
      ↓
FeistelUtils.encrypt(id)     ← 新增：双射置换，id=1000000 → 4195963162
      ↓                        （连号 → 无规律，[0, 2^32-1] 一一对应）
Base62Utils.encode(shuffled) ← 不变：纯进制转换
      ↓
short_code 存 DB + 加布隆 + 写 Redis（后续逻辑全部不变）
```

`ShortUrlServiceImpl.createShortUrl` 实际改动就 1 行：

```java
// 阶段1~4: String shortCode = Base62Utils.encode(shortUrl.getId());
String shortCode = Base62Utils.encode(FeistelUtils.encrypt(shortUrl.getId()));
```

### 3.2 跳转链路（零改动，历史数据全兼容）

跳转是 `WHERE short_code = ?` **按短码字符串直接查 DB**，不依赖 id 反解：

- 老短码（`4c9g` 这类 Base62(id) 直编）：按字符串查，照常命中
- 新短码（`4zXPHc` 这类 Feistel 后编码）：同样按字符串查
- 两种格式在一张表里共存，DB 实测验证：id=1000020 短码 `4c9m`（旧格式）、id=1000021 短码 `2jRmiR`（新格式），跳转路径对两者无感知

## 五、关键设计点（面试可讲）

### 5.1 短码生成方案淘汰赛（为什么选 Feistel）

| 候选 | 原理 | 致命伤 |
|---|---|---|
| 随机 Base62（掷骰子） | `encode(randomLong)`，DB 唯一索引兜底，撞了重抽 | ① 号码池越深写入放大越狠：占用 90% 时平均要掷 10 次 = 创建 1 条打 10 次 DB INSERT；② 不可逆，排查只能查库；③ `Random` 种子可预测、`SecureRandom` 耗熵池慢 100 倍，两头别扭 |
| MD5(id) 截断 | 哈希后取前几位编码 | ① 生日悖论，容量几十万后碰撞概率飙升，撞了要 DB 兜底重试；② 不可逆 |
| **Feistel 双射置换** ✅ | 置换打乱 id 再编码 | 无硬伤。零碰撞（不用 DB 兜底重试）、可逆（运维反解）、纯位运算纳秒级。代价：多写 ~100 行板子 + KEYS 上线不能改 |

**一句话**：短链创建是「一抖就批量失败」的敏感路径，拿 100 行代码换「创建永不重试 + 运维可反解」，ROI 为正。

### 5.2 Feistel vs 哈希的本质（最容易被追 问混的概念）

> **Feistel 的目标 = 置换 + 可逆 → 天然附带「零碰撞」红利**
> **哈希的目标 = 压缩 + 单向 → 天然附带「碰撞风险」trade-off**

| 维度 | Feistel / 分组密码 | 哈希（MD5/SHA256） |
|---|---|---|
| 输入输出 | 定长 → **同尺寸**（32bit→32bit） | 任意长 → 固定短（1GB→32B） |
| 可逆 | ✅ decrypt 存在 | ❌ 信息丢了回不去 |
| 碰撞 | **数学 0 概率**（双射） | 必然存在（鸽巢原理），位数大只是概率低 |
| 比喻 | 扑克牌完美洗牌（54 张进去 54 张出来） | 榨汁机（整头牛进去一杯汁出来） |
| 主场 | 短链 ID 混淆、对称加密（AES/DES） | 密码存储、文件校验、去重指纹、签名 |

### 5.3 为什么零碰撞（面试官抬杠「洗牌也可能撞」时怎么答）

**归谬证明**：完美洗牌是函数，且存在逆函数（逆着洗一遍就还原）。假设两副不同牌 A、B 洗完都是 C → 对 C 逆洗，结果到底是 A 还是 B？函数每个输入只有一个输出 → 矛盾 → 碰撞不存在。

**哈希为什么必然撞**：输入空间 2^8192（1KB 文件）挤进输出空间 2^256 → 鸽巢原理，神仙写的也一样撞。**可逆（有逆函数）→ 一一对应 → 零碰撞；压缩丢信息 → 必然撞。这是函数映射的本质，与算法牛不牛无关。**

**为什么哈希不学 Feistel**：不是做不到，是设计目标相反——① 一压缩（任意长→固定短）就必然鸽巢碰撞；② 一可逆就是灾难：密码可还原 = 数据库泄漏全裸奔、签名可反解 = 商业机密曝光。**不可逆是哈希的 feature 不是 bug**（bcrypt 存密码、SHA256 秒传去重，都指着单向活着）。

### 5.4 澄清误区：零碰撞不是「拿空间换的」

encrypt 输入 32 位、输出还是 32 位，**没多占 1 bit**。零碰撞是「定长 + 可逆」数学结构自带的免费属性。

真正「用空间换容量」的是**短码位数本身**：4 位 Base62 = 1477 万组合、5 位 = 9.16 亿、6 位 = 568 亿。Feistel 只是在你选定的容量范围内，把连号 id 无损打乱——好比 5 个房间（容量）没多修，只把门牌号换了（混淆）。

### 5.5 id 为什么保持自增不动（只混淆 shortCode）

| 理由 | 说明 |
|---|---|
| 索引性能 | 自增 id → B+ 树顺序插入零碎片；id 打乱 = 随机插入页分裂，写入掉档 |
| 零迁移 | 老数据 id 不动，跳转按 short_code 查，v1~v4 全兼容 |
| 分页排序 | `ORDER BY id DESC` 天然按创建时间倒序，白嫖自增特性 |

> **id 是数据库的内部骨架，乱了拆家；shortCode 是对外的门牌号，乱了防贼。各司其职。**

### 5.6 decrypt 的定位（业务不用，但必须存在）

跳转按 short_code 查库，`shortUrl.getId()` 现成的——**decrypt 不在业务链路上**。它服务三类场景：

1. **运维排查**：Nginx 日志里 100 万条短码要 join 回 DB 统计 → `decrypt(decode(code))` 纯 CPU 批量反解 0.3 秒，对比 `WHERE short_code IN (...)` 分批查快百倍
2. **脏数据判定**：怀疑 short_code 被人手改 → 反解出 id 与 DB 记录的 id 比对，不等 = 铁定被改，不用写 SQL 猜
3. **双射自证**：存在完美逆函数 = 从代码层面证明一一对应，比跑 100 万次判重更硬的零碰撞证据

注意：阶段1~4 老短码是 `Base62(id)` 直编不经 Feistel，反解老码直接 `decode` 结果就是 id，不要过 decrypt。

### 5.7 KEYS 保护三道枷锁（同事改了子密钥怎么办）

KEYS 一改，老短码永远对不上 id（同 id 生成出不同短码）。防护：

1. **代码层**：`private static final int[] KEYS` + 注释「上线后绝对禁止修改」
2. **单测层**：黄金值回归锚点——`assertEquals(4195963162L, encrypt(1_000_000L))`，KEYS/轮数/轮函数任何改动立刻红，CI 拦住
3. **流程层**（如果上团队）：该文件设 Code Owner，改动必须指定 review

顺带回答「KEYS[3] 改成 0x0000 会怎样」：性能不变（指令数没差）、碰撞仍为零（零碰撞是 Feistel 结构保证的，与 KEYS 无关），**真正的灾难是新旧短码分裂**——同一个 id 前后生成出两个不同短码，统计全乱。

### 5.8 容量预案（32 位 43 亿用完了怎么办）

- **现状够用**：2^32 ≈ 43 亿，国内一线大厂短链累计量级也够
- **预案 1**：块扩到 64 位（左 32 + 右 32），KEYS 换 64 位扩散常数，容量 1.8e19；新老 id 按阈值走不同位数
- **预案 2**：短码扩 1 位（62 倍容量），业务零感知，URL 多 1 个字符
- DB id 本身是 BIGINT 64 位，结构没堵死

## 七、踩坑记录（重要！）

### 坑 1：`encrypt` 的 `result==0` 兜底破坏双射（提交前复查揪出，必讲）

**初版代码**：

```java
// 理论上 result=0 只有 id=0 才会出现，但 id=0 已被前置拦截，这里兜底
return (result == 0L) ? 1L : (result & MAX_32);   // ❌ 错误
```

**注释里的推理是错的**。全空间双射中，恰好有**一个 id（= decrypt(0)，在 43 亿空间某处，一般不是 0）**映射到 0。兜底把它改成 1 后，它就和 `encrypt(decrypt(1))` 撞车——**零碰撞承诺破功**。

**为什么 100 万单测没抓到**：那个特定 id > 100 万（HashSet 判重只扫了 1~100 万），测试通过纯属该值恰好不在扫描范围内。这正是「测试通过 ≠ 数学性质成立」的活例子。

**修复**：
- encrypt：0 原样返回（短码 `"0"` 是 1 位合法短码，格式校验 `^[0-9a-zA-Z]{1,10}$` 通过，跳转按字符串查库无影响），输入放行 0 保证 encrypt/decrypt 互为完美逆函数
- decrypt：放行输入 0
- 单测：删掉与修复矛盾的 `encrypt_shouldNeverReturnZero`，新增 `encrypt_zeroOutputEdge_shouldStayBijective`（锁死「0 必须原样映射」，谁再加兜底立刻红）和 `encrypt_goldenValues_shouldStayStable`（KEYS 回归锚点）

**面试加分讲法**：「我的 Feistel 零碰撞一开始有个数学漏洞——为了避开输出 0 加了个兜底改值，恰好破坏了双射。提交前复查时靠归谬推理发现：全空间恰好有一个 id 映射到 0，兜底改 1 就跟 decrypt(1) 的原像撞车。100 万单测没抓到是因为那个 id 在 43 亿空间里。这让我意识到：**结构性保证（双射）不能靠抽样测试验证，要靠数学推理 + 边界用例锁死**。」

本机系统默认 JDK 不是 17，直接跑 `mvn.cmd test` 编译失败。

## 九、简历口径

### 可写

> - 定位短码连号可枚举的信息泄露漏洞（IDOR 变体），用 Feistel 网络双射置换治理：自增 id 经 32 位块 10 轮置换后再 Base62 编码，相邻 id 生成的短码完全无规律
> - 双射性质保证零碰撞（创建链路无需 DB 查重重试）且可逆（支持从短码离线反解 id，运维排查零 DB 查询）；100 万连续 id 实测可逆率 100%、碰撞 0 次
> - 仅改生成路径 1 行代码，跳转/缓存/布隆/MQ 统计链路零改动，新旧短码同表共存全兼容
> - 用黄金值回归测试锁死加密参数（KEYS/轮数），防止后续改动导致老短码失效；提交前复查发现并修复「输出 0 兜底破坏双射」的数学漏洞

### 不可写

- ❌ 「枚举命中率 10%→0%」当实测数据讲（是推算，被追问压测细节会露馅；要讲就标明推算依据）
- ❌ 「自研加密算法」（Feistel 是 DES/AES 的经典公开结构，我们只是按标准结构实现了业务版，说「自研」会被密码学向面试官吊打）
- ❌ 「绝对安全/防爬虫」（防的是**可预测性**，不是防 DDoS；真要防爬还得上层限流）

### 面试 30 秒定稿话术

> 「短码原来是 Base62(自增 id)，完全连号，for 循环能爬光全部短链。我用 Feistel 网络做双射置换：它和哈希本质不同——哈希是压缩+单向所以必然碰撞，Feistel 是同尺寸置换+可逆，数学上零碰撞且能反解。选它不选随机短码，是因为随机方案号码池深了会写入放大、还不可逆。改动只有生成路径 1 行，跳转按 short_code 查库所以历史数据全兼容。加密参数用黄金值单测锁死，谁改参数 CI 立刻红。」
