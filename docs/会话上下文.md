## 四、阶段5 核心设计（代码链路速查）

**生成**（唯一改动）：`createShortUrl` 中 `Base62Utils.encode(FeistelUtils.encrypt(shortUrl.getId()))`。
**跳转**（零改动）：`WHERE short_code = ?` 按字符串查库，对新旧短码无感知。

- `FeistelUtils.encrypt(id)`：id → 打乱后的混淆 id，双射（输入输出同 32 位，[0, 2^32-1] 一一对应）
- `decrypt(shuffledId)`：完美逆函数，业务不用（跳转不反解），运维排查/脏数据判定/双射自证用
- KEYS 子密钥数组上线**绝对禁改**——黄金值回归测试锁死（`encrypt(1_000_000)=4195963162` → `4zXPHc`，改参数单测立刻红）
- 面试核心结论：Feistel=置换+可逆→零碰撞红利；哈希=压缩+单向→碰撞 trade-off；零碰撞是「定长+可逆」数学结构自带，不是空间换的（短码位数才是空间换容量）
- 阶段5 踩坑（面试加分素材）：初版 encrypt 的 `result==0 兜底改 1` 破坏双射——全空间恰有一个 id（=decrypt(0)）映射到 0，兜底与 `encrypt(decrypt(1))` 撞车；100 万单测没抓到是因为该 id>100 万。教训：**结构性保证不能靠抽样测试验证，要靠数学推理+边界用例锁死**。

## 四A、阶段4 核心设计（保留速查）

入口 `ShortUrlServiceImpl.getOriginalUrl`（L213）按 `cache-guard.mode` 分发：
- `none` → `getOriginalUrlUnguarded`（L229-245）：阶段1~3 原逻辑，**故意不改**，作 A/B 基线
- `mutex` / `logical-expiry` → `getOriginalUrlGuarded`（L255）：四道防线

**穿透**（红色层，让"不存在"被记住/预判）：
1. 格式校验 `isValidShortCode`（L582-584，正则 `^[0-9a-zA-Z]{1,10}$`）
2. 布隆过滤器 `bloomFilter.mightContain`（L262-266）→ `RedisBloomFilter` 薄包装层包装 Redisson `RBloomFilter`（Redis Bitmap 共享持久，n=100 万 / p=1%，墙约 1.2MB；Redisson 内部 Lua 压 k 次 GETBIT 成 1 往返）
3. 空值缓存 `NULL_MARK`（TTL 120s）：`queryDbAndWriteBack`(L417-438) 查不到写空值；`writeCacheValue`(L451-470)

**击穿**（琥珀色层，过期瞬间只 1 个线程回源）：
- `mutex`：`getWithMutex`（L288-354）抢锁 tryLock + 双重检查 + finally 只解自己的锁（`RedisLock.unlock` Lua 比对 value 防误删）
- `logical-expiry`：`getWithLogicalExpiry`（L367-408）返回旧值 + 异步重建（线程池 `CallerRunsPolicy`），值过期时间存 `CacheValue`(`u`/`e`/`n`)，不能靠 Redis TTL 消失

**可观测（压测脚手架，生产也建议留）**：
- `CacheGuardMetrics`（11 个 AtomicLong，关键指标 `dbQuery` 在 `queryDbAndWriteBack` L418 自增，全项目唯一处）
- `ShortUrlController` 两个接口：`GET /api/short-url/cache-guard/metrics`、`POST /api/short-url/cache-guard/metrics/reset`
- `none` 模式：纯对照组，生产永不配
